# Архитектурное решение по трейсингу

## 1. Системы, которые следует покрыть трейсингом

Заказ в «Александрите» проходит через 10 статусов и **физически переходит между тремя
независимыми приложениями** (онлайн-магазин → CRM → MES), которые общаются через
HTTP API и асинхронную шину RabbitMQ. Это и есть те границы, на которых заказ может
«сломаться» или «зависнуть».

| # | Компонент | Почему покрывать | Что измерять |
|---|---|---|---|
| 1 | **Shop API** (Spring Boot) | Точка входа для двух каналов — B2C (через UI) и B2B (через API). На обоих сценариях создаётся заказ; здесь же грузятся 3D-файлы. | Каждый входящий HTTP-запрос → корневой спан; вызовы Shop DB и 3D-storage — дочерние. |
| 2 | **CRM API** (Spring Boot) | Получает события от MES (PRICE_CALCULATED), отправляет MANUFACTURING_APPROVED. Часто упоминается в жалобах «заказ остановился». | Входящие HTTP + потребление сообщений из RabbitMQ + публикация сообщений в RabbitMQ. |
| 3 | **MES API** (C#) | Расчёт цены — самая долгая операция (2–30 мин). Главный кандидат на «зависшие» заказы. | Входящие HTTP + длинный спан расчёта цены + публикация/потребление RabbitMQ. |
| 4 | **RabbitMQ (как канал)** | Сообщения между MES и CRM теряются. Здесь же стык B2B-сценария «MES сам инициирует заказ через API». | RabbitMQ сам по себе не источник спанов, но **trace context должен быть встроен в свойства сообщений** (W3C `traceparent` в headers), чтобы спан-producer и спан-consumer попали в один трейс. |
| 5 | **3D files storage (S3)** | Загрузка тяжёлых 3D-файлов — потенциальный источник медленных операций и таймаутов. | Auto-instrumentation для S3 SDK; спан с размером файла. |
| 6 | **Shop DB / MES DB / CRM DB (PostgreSQL)** | Медленный дашборд MES (см. Task 1 / Task 5). Long-running SQL — частая причина зависания статуса. | Auto-instrumentation JDBC/ADO.NET — каждый SQL = спан, с `db.statement` (без чувствительных параметров). |
| 7 | **Internet Shop UI** (Vue) — на втором этапе | UX-метрики: сколько занимает у пользователя от «корзина» до «заказ создан». | OTel browser SDK, корневой спан пользовательской сессии (опционально). |

**На схеме (`jewerly_c4_model_tracing.drawio`)** все охваченные трейсингом компоненты
обозначены **красными связями** к OpenTelemetry Collector. Boundary `Observability
Platform` (красный) — новые компоненты трейсинг-стека.

### Где заказ может «сломаться» — карта типовых проблем

| Этап | Симптом, который покажет трейсинг |
|---|---|
| SUBMITTED → PRICE_CALCULATED | Спан в MES API длится 30+ мин или отсутствует вовсе → расчёт повис или сообщение не дошло. |
| PRICE_CALCULATED → MANUFACTURING_APPROVED | Сообщение опубликовано MES в RabbitMQ, но нет consumer-спана в CRM → потеряно. |
| MANUFACTURING_STARTED → MANUFACTURING_COMPLETED | Длительный gap между спанами → реальная производственная задержка, не IT-проблема. |
| CLOSED | Сообщение от транспортной компании не дошло (внешняя интеграция) → видно по отсутствию входящего спана. |

## 2. Данные в трейсинге

### 2.1 Обязательные поля (стандарт W3C/OTel)
- `trace_id` (16 байт, hex) — общий идентификатор сквозной операции.
- `span_id` / `parent_span_id` — иерархия.
- `service.name` — `shop-api`, `crm-api`, `mes-api`, `price-calc-worker`, ...
- `operation_name` — `POST /api/orders`, `calculate_price`, `consume order.events`, ...
- `start_time`, `duration`.
- `status` — `OK` / `ERROR` (+ описание).

### 2.2 HTTP-атрибуты (semantic conventions)
- `http.method`, `http.route`, `http.status_code`, `http.url`.
- `net.peer.name`, `net.peer.port`.
- `user_agent.original` (без PII).

### 2.3 Бизнес-атрибуты (наш кастомный набор)
- `order.id` — для поиска конкретного заказа в Jaeger UI; **наш самый ценный bridge**
  от жалобы клиента к данным.
- `order.channel` — `b2c` или `b2b`. Позволяет фильтровать трейсы по каналу
  (повторяет важный ярлык метрик из Task 2).
- `order.status_from`, `order.status_to` — для span'ов смены статуса.
- `customer.id` — техническая ссылка (см. ограничения в разделе 6 — без ПДн).
- `price_calculation.complexity_bucket` — `low` / `medium` / `high`.
- `price_calculation.polygon_count` — численный размер 3D-модели.
- `price_calculation.cache_hit` — `true` если ответили из кеша (когда будет реализован).
- `b2b_partner.id` — для B2B-канала.

### 2.4 БД-атрибуты (через auto-instrumentation)
- `db.system` — `postgresql`.
- `db.name` — `shop`, `mes`, `crm`.
- `db.statement` — текст SQL (**параметры — placeholder'ами, не значения**, см. безопасность).
- `db.rows_affected`.

### 2.5 Шина (RabbitMQ)
- `messaging.system` — `rabbitmq`.
- `messaging.destination` — название exchange/queue.
- `messaging.message.id` — `message_id` сообщения (для идемпотентности; см. Task 1).
- `messaging.operation` — `publish` / `receive` / `process`.

### 2.6 Чего НЕ кладём
- ФИО, email, телефон, адрес доставки — **PII**.
- Содержимое сообщения / тело HTTP-запроса (может содержать PII или коммерческую информацию).
- Картинки 3D-моделей (только мета: размер, формат, кол-во полигонов).
- Любые токены/пароли/секреты.

(Подробнее — раздел 7 «Безопасность».)

## 3. Мотивация

### Зачем трейсинг
Сегодня команда не может объяснить, **где** заказ застрял. Текущие логи разрозненны
(каждый сервис пишет в свой файл), у каждой подсистемы — своя терминология,
сопоставить «заказ X из жалобы клиента» с «вот этим спайком в CRM три часа назад»
почти невозможно. Трейсинг даёт **один уникальный `trace_id`**, по которому за пару
кликов поднимается **вся цепочка событий** для конкретного заказа — от UI до БД.

Это решает сразу несколько боли из Task 1:
- **«Пропавшие» заказы (P6)** — видно, в каком сервисе цепочка спанов оборвалась.
- **«Зависшие» заказы (P2, P4)** — видно, какой именно спан длится аномально долго.
- **Жалобы B2B-партнёров (P10)** — у саппорта появляется доказательная база для
  диалога с партнёром («ваш заказ id=42 завис на расчёте, не на нашей очереди»).
- **Долгий разбор инцидентов поддержкой (P1)** — на порядок ускоряется.

### Технические и бизнес-метрики решения, на которые повлияет трейсинг

| Метрика | Тип | Текущее значение | Целевое после трейсинга |
|---|---|---|---|
| **MTTR** (mean time to resolve инцидент с заказом) | Тех. | часы / дни (опрос клиента) | минуты (поиск по `order.id` в Jaeger) |
| **Доля «нераскрытых» жалоб** (нашли причину / не нашли) | Тех./бизнес | высокая | стремится к нулю |
| **% заказов, по которым партнёр получил ответ о статусе менее чем за 30 мин** | Бизнес/SLA | ? (нет данных) | >95% |
| **Доля времени саппорта, потраченная на диагностику vs. на коммуникацию с клиентом** | Тех. | смещена в диагностику | смещается в коммуникацию |
| **P99 длительности расчёта цены `price_calculation_duration_seconds`** | Тех. | неизвестно | будет измеримой величиной → можно ставить SLO |

## 4. Предлагаемое решение

### 4.1 Технологии

- **Источники спанов:** OpenTelemetry SDK для каждого языка стека:
  - **Java** (Shop API, CRM API): `opentelemetry-java` + `opentelemetry-spring-boot-starter`
    или `opentelemetry-javaagent` (auto-instrumentation, нулевые изменения в коде).
  - **C#** (MES API): пакет `OpenTelemetry`, `OpenTelemetry.Instrumentation.AspNetCore`,
    `OpenTelemetry.Instrumentation.SqlClient`, `OpenTelemetry.Exporter.Otlp`.
  - **JS** (UI на втором этапе): `@opentelemetry/sdk-trace-web` + `@opentelemetry/instrumentation-fetch`.
- **Транспорт:** **OTLP/HTTP** (или gRPC). Это вендоронезависимый стандарт, который
  поддерживают и Jaeger, и Tempo, и Honeycomb, и любая SaaS-платформа. Сменить
  бэкенд через 2 года — конфиг collector'а, не код приложения.
- **Сборщик:** **OpenTelemetry Collector** (deployment в K8s, namespace `observability`).
  Buffer, batching, **tail-based sampling** (сохраняем 100% «медленных» и `ERROR`
  трейсов, 1–5% «нормальных», чтобы не похоронить хранилище под B2C-трафиком).
- **Бэкенд хранения и UI:** **Jaeger** (collector + query + UI), для prod — внешнее
  хранилище **Elasticsearch / OpenSearch** (retention 14 дней hot, 30 дней cold).
- **Propagation:** W3C Trace Context (стандартные HTTP-заголовки `traceparent`/`tracestate`).
  Через RabbitMQ — пробрасывается в **message properties** (поле `headers`),
  поддерживается всеми OTel-инструментациями RabbitMQ.

### 4.2 Компоненты и связи

Доработанная C4-диаграмма: **[`jewerly_c4_model_tracing.drawio`](./jewerly_c4_model_tracing.drawio)**.

Новые элементы выделены **красным**:
- Boundary **Observability Platform**.
- Контейнер **OpenTelemetry Collector** — принимает OTLP от всех бэкендов.
- Контейнер **Jaeger Backend** — collector + query.
- Контейнер **Trace Storage** — Elasticsearch/OpenSearch.
- Актор **Support Engineer** — пользователь Jaeger UI.
- Связи: каждый бэкенд (Shop API, CRM API, MES API) → OTel Collector → Jaeger → Trace Storage.

### 4.3 Что добавится в код

- В каждом бэкенде — инициализация SDK с указанием OTLP endpoint
  (`http://otel-collector.observability:4318`).
- В кодовых местах смены статуса заказа — добавить кастомные атрибуты на текущий спан:
  `order.id`, `order.channel`, `order.status_to`.
- В producer/consumer RabbitMQ — конфигурация OTel-instrumentation, чтобы
  `traceparent` автоматически клался в message properties.

### 4.4 Поэтапное внедрение

Команда не сможет покрыть всё одновременно. Порядок (в первую очередь — самые громкие
проблемы):

1. **Spring Boot бэкенды (Shop API, CRM API).** Auto-instrumentation через javaagent
   — буквально одна переменная окружения. Минимум изменений, максимальный эффект.
2. **MES API (C#) + RabbitMQ propagation.** Здесь — ядро боли, и здесь же — больше
   всего ручной работы (расчёт цены — кастомный код).
3. **Бизнес-атрибуты и кастомные спаны на сменах статуса.**
4. **3D files storage + PostgreSQL via auto-instrumentation.**
5. **UI (browser OTel SDK).** Самая необязательная часть.

### 4.5 [Доп.] Автоматический мониторинг прохождения заказа и алертинг

> Доп. задание: автоматический мониторинг + алертинг на основе данных трейсинга.

Доработанная диаграмма с алертингом: **[`jewerly_c4_model_tracing_alerting.drawio`](./jewerly_c4_model_tracing_alerting.drawio)**.
Новые элементы — **зелёным**.

Идея — превратить **поток спанов в метрики**, а на метрики **навесить алёрты**.
Стандартная пайплайн в современном OTel-стеке:

```
OTel Collector
  ├─ exporter: jaeger   (хранение трейсов для ручной диагностики)
  └─ connector: spanmetrics   (генерирует Prometheus-метрики из спанов)
                    ↓
                Prometheus  (scrape /metrics)
                    ↓
               Alertmanager
                    ↓
            Slack / PagerDuty
```

#### Что считаем алерт-триггером (правила Prometheus)

| Правило | Условие | Severity | Действие |
|---|---|---|---|
| **Order stuck** | `order_status_duration_seconds{to="PRICE_CALCULATED"} p99 > 600` 10 мин подряд | warning | Slack-канал #ops |
| **Order lost** | `order_pipeline_gap_total{from="PRICE_CALCULATED",to="MANUFACTURING_APPROVED"} > 0` (есть PRICE_CALCULATED, но нет MANUFACTURING_APPROVED 30+ мин) | critical | PagerDuty + page on-call |
| **Slow price calculation** | `histogram_quantile(0.95, price_calc_duration) > 1800s` | warning | Slack |
| **B2B SLA breach** | `order_response_time{channel="b2b"} > 60s` | critical | PagerDuty + уведомление аккаунт-менеджеру партнёра |
| **Trace gap** | `rate(spans_total{status="UNSET"}[5m]) > 10%` | warning | Slack — проблема с инструментацией |

#### Преимущество над метриками «в чистом виде»
Spanmetrics — это **метрики, выведенные из реальных пользовательских трасс**.
Они дают точно то же, что и инструментация метриками вручную, но **бесплатно**: спаны
уже отправляются → не нужно отдельно поддерживать набор бизнес-метрик в коде каждого
сервиса.

## 5. Компромиссы

Где трейсинг **не помогает** или его внедрение **дорого**:

| Проблема | Почему трейсинг не решает |
|---|---|
| **Производственная задержка (не IT)** | Если заказ в статусе MANUFACTURING_STARTED три недели — это про оператора у станка, а не про систему. Трейсинг покажет «всё нормально, никаких аномалий в коде», и это будет правильный ответ. |
| **Браузерный фронтенд первичной важности** | Internet Shop UI на Vue + Three.js — много рендеринга в WebGL. OTel browser SDK покрывает HTTP-вызовы, но не рендеринг 3D. Сюда лучше Яндекс.Метрика + web-vitals (см. Task 2). |
| **MES до распила** | Сейчас MES — монолит на C# с кастомным расчётом цены. Auto-instrumentation покроет HTTP/DB, но **кастомные шаги расчёта** придётся инструментировать вручную. Это может быть дорого, если код легаси и плохо структурирован. |
| **Транспортная компания и другие внешние системы** | Их трейсинг не покроет — мы не их клиенты. Видны только «края»: исходящий HTTP-вызов с нашей стороны, потом тишина. |
| **High-throughput / low-latency пути** | Если в системе появится hot path с RPS > 10k и латентностью < 10 мс (например, чтения из кеша) — трейсинг каждого запроса будет дорого. Решение: head-based sampling с малым процентом, либо отказ от инструментации hot path'а. |
| **Чувствительные данные** | Если в спане окажется PII — нужно либо процессор-санитайзер в Collector'е (`attributes processor` с `delete`/`hash`), либо отказ от автоинструментации в некоторых местах. |
| **Прод-расходы на хранение** | В нашем случае при ~500 заказов в день и средней цепочке ~30 спанов — это 15K спанов/день. Это около 30 МБ/день в Elasticsearch — мизер. Но если перейти к высокочастотным health-checks или RPS вырастет в 100× — нужно tail-sampling. |

## 6. Безопасность

### 6.1 Внутри компании — Jaeger UI

| Угроза | Мера |
|---|---|
| Любой сотрудник видит трейсы клиентов | **Аутентификация** через корпоративный SSO (OIDC/SAML). Доступ только сотрудникам с активной учётной записью. |
| Инженер видит трейсы за пределами своей ответственности | **Авторизация по ролям**: `support` (RO ко всем трейсам), `dev` (RO к трейсам своего сервиса), `sre` (RW ко всему, включая управление настройками). Внутри Jaeger 1.5x это организуется внешним reverse-proxy (oauth2-proxy + RBAC), либо переходим на **Grafana Tempo** + Grafana — там RBAC встроенный. |
| Утечка PII в спанах | **Sanitization в Collector**: `attributes processor` с правилами `delete(http.request.body)`, `hash(customer.email)`, и т.д. Аудит атрибутов **обязателен** при подключении нового сервиса. |
| Утечка `db.statement` с чувствительными значениями | Auto-instrumentation JDBC/ADO.NET по умолчанию заменяет значения параметров на placeholder'ы (`SELECT * FROM users WHERE id = ?`). Проверить, что эта опция включена. |
| Логи Collector'а попадают в Loki/файлы | Уровень логирования Collector'а — `WARN`, без дампа payload'ов. |

### 6.2 Снаружи компании

- Jaeger UI **никогда** не выставляется в публичный интернет. Доступ только через
  корпоративный VPN или SSO-портал.
- OTel Collector принимает трафик **только из приватной сети** (или из K8s namespace,
  если переедем). Никакого публичного endpoint.
- Если B2B-партнёрам нужно показывать статус их заказов — это **отдельный B2B-портал**
  с собственным API, читающим из БД (или из спецсервиса), а не Jaeger UI. Спаны —
  это внутренний инструмент инженеров.

### 6.3 На уровне SDK
- Не отключать TLS между сервисами и Collector в prod (даже внутри VPC):
  `OTEL_EXPORTER_OTLP_ENDPOINT=https://...`.
- В лабе/dev — `WithInsecure()` допустимо.

## 7. Реализация MVP — Task 3.1 (OpenTelemetry + Jaeger в Kubernetes)

> Это вторая половина задания — практическая лаба.

### Что сделано

В папке [`architecture-alexandrite-k8s-trace-main/`](./architecture-alexandrite-k8s-trace-main/):

- **`k8s/jaeger-instance.yaml`** — Custom Resource для Jaeger Operator. AllInOne
  стратегия (collector + query + UI в одном поде), in-memory storage на 100k трейсов
  (для лабы достаточно; в prod — Elasticsearch).
- **`k8s/services.yaml`** — Deployment + Service для двух тестовых сервисов
  `service-a` и `service-b`, по порту 8080.
- **`services/service-a/`** — Go-сервис: REST-эндпоинт `GET /`, делает HTTP-вызов к
  `service-b` и возвращает результат. Инструментирован OpenTelemetry SDK.
- **`services/service-b/`** — Go-сервис: REST-эндпоинт `GET /`, эмулирует работу
  случайной задержкой 50–250 мс (чтобы спан имел видимую ширину в Jaeger UI).

### Стек инструментации в коде сервисов

```go
import (
    "go.opentelemetry.io/contrib/instrumentation/net/http/otelhttp"
    "go.opentelemetry.io/otel"
    "go.opentelemetry.io/otel/exporters/otlp/otlptrace/otlptracehttp"
    "go.opentelemetry.io/otel/propagation"
    "go.opentelemetry.io/otel/sdk/resource"
    sdktrace "go.opentelemetry.io/otel/sdk/trace"
    semconv "go.opentelemetry.io/otel/semconv/v1.26.0"
)
```

Ключевые моменты:
- Экспортёр **OTLP/HTTP** в `simplest-collector.observability.svc.cluster.local:4318`.
- Resource-атрибут `service.name` (попадает в Jaeger как имя сервиса).
- HTTP сервер и клиент обёрнуты в `otelhttp.NewHandler` / `otelhttp.NewTransport` —
  всё трассирование «бесплатно».
- TextMapPropagator = `TraceContext` (W3C). Заголовок `traceparent` передаётся
  автоматически клиентом и читается сервером.

### Команды для запуска

```bash
# 1. Кластер
minikube start -p alexandrite --memory=6g --cpus=4 --driver=docker --force

# 2. cert-manager (зависимость jaeger-operator)
kubectl apply -f https://github.com/cert-manager/cert-manager/releases/download/v1.13.3/cert-manager.yaml

# 3. jaeger-operator
kubectl create namespace observability
kubectl create -f https://github.com/jaegertracing/jaeger-operator/releases/download/v1.51.0/jaeger-operator.yaml -n observability
```

### Результат

Один пользовательский запрос → **один trace** из **четырёх спанов**:

```
[service-a] GET /              (root, ~107 ms)
  └─ [service-a] HTTP GET      (исходящий клиентский к service-b)
      └─ [service-b] GET /     (входящий серверный)
          └─ [service-b] process-request   (внутренний)
```

Trace context корректно пробросился между подами через HTTP-заголовок `traceparent` —
именно то, чего сейчас нет у «Александрита». Скриншот Jaeger UI с найденным трейсом —
**[jaeger_trace_screenshot.png](./jaeger_trace_screenshot.png)**.

### Что лаба показала на практике
1. **Стоимость инструментации Go-сервиса** — ~50 строк boilerplate-кода для инициализации
   SDK. Для Spring Boot будет ещё меньше (один javaagent).
2. **Propagation работает «из коробки»** — пробрасывание `traceparent` не требует
   написания кода в каждом вызове.
3. **Jaeger UI читабелен** — поиск по `service`, `operation`, `tags`, диапазону длительности.
4. **Latency overhead на пустом запросе** — пренебрежимо мал (< 1 мс), батчинг
   в `BatchSpanProcessor` сглаживает нагрузку на Collector.

## 8. Резюме

- **Покрыть трейсингом**: Shop API, CRM API, MES API, RabbitMQ-обвязку, 3D-storage, PostgreSQL.
- **Стек**: OpenTelemetry SDK (Java/C#/JS) → OTel Collector → Jaeger → Elasticsearch.
- **Кастомные атрибуты** — `order.id`, `order.channel`, `order.status_to` — превращают
  абстрактный «трейс HTTP-запроса» в инструмент диагностики **именно** проблем
  «Александрита».
- **Доп. ценность** — spanmetrics processor: те же спаны, что хранятся в Jaeger,
  генерируют Prometheus-метрики для алертинга. Не нужно дублировать инструментацию.
- **MVP в Kubernetes** реализован и работает: 2 сервиса на Go с OTel SDK,
  Jaeger через jaeger-operator, видимый трейс из 4 спанов.
- **Безопасность** — Jaeger UI за SSO, OTel Collector — только во внутренней сети,
  процессоры-санитайзеры на уровне Collector для PII.
- **Компромиссы** — не помогает с производственными задержками, дорог при auto-instrumentation
  плохо структурированного легаси-кода MES, требует tail-sampling при росте трафика
  в десятки раз.
