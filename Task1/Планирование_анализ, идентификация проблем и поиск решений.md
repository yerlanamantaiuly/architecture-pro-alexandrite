# Планирование. Анализ, идентификация проблем и поиск решений

## 1. Контекст

Компания «Александрит» — производство ювелирных украшений, в том числе по индивидуальному дизайну.
В систему входят три приложения: **Онлайн-магазин** (Vue + Spring Boot), **CRM** (Vue + Spring Boot)
и **MES** (React + C#). Связь MES ↔ CRM — через RabbitMQ. Расчёт стоимости делает MES
(2–30 минут на изделие в зависимости от сложности 3D-модели).

В 1-м квартале компания вышла на новые рынки, во 2-м открыла внешний API для B2B-партнёров.
Нагрузка растёт на ~100 заказов/месяц. На этом фоне:

- клиенты жалуются на «пропавшие» и «зависшие» заказы;
- партнёры через API получают то же самое;
- операторы MES жалуются на медленную загрузку дашборда;
- релизы регулярно задерживаются из-за ручного E2E.

Производственные мощности не являются узким местом — они выдерживают двукратный рост.
Значит, проблема в IT-ландшафте.

## 2. Идентификация проблем

### 2.1 Существующие проблемы

| # | Проблема | Где проявляется | Почему болит |
|---|---|---|---|
| P1 | Нет наблюдаемости (метрик, трейсинга, централизованных логов) | Везде | Команда не может ответить, **где** и **почему** заказ зависает. Все остальные исправления идут вслепую. |
| P2 | Долгий расчёт стоимости в MES (2–30 мин) выполняется синхронно | MES API | Один тяжёлый заказ блокирует поток. При росте трафика очередь расчёта растёт нелинейно. |
| P3 | MES — единая точка обработки и B2C, и B2B потоков | MES API | После открытия API нагрузка удвоилась, MES не справляется. Нет изоляции потоков. |
| P4 | Медленный дашборд MES даже с фильтром и пагинацией | MES UI | Скорее всего тяжёлые JOIN/COUNT по большой таблице, нет индексов под фильтр, нет кеша. Операторы теряют вознаграждение. |
| P5 | Single-instance каждого приложения и каждой БД | Вся инфраструктура | Точка отказа + нечем масштабироваться. Read нагрузка идёт на тот же инстанс, что write. |
| P6 | Сообщения между MES и CRM могут теряться | Шина RabbitMQ | Нет идемпотентности обработчиков и нет DLX — потерянные/неподтверждённые сообщения исчезают без следа. Прямая причина «пропавших» заказов. |
| P7 | Ручное E2E-тестирование — узкое место релизного цикла | QA-процесс | Релизы стабильно задерживаются, последние месяцы — больше месяца. Тормозит выкатку фиксов. |
| P8 | Деплой на release и prod вручную | CI/CD | Удлиняет MTTR при инциденте, бьёт по скорости подачи фиксов клиентам. |
| P9 | API для B2B без rate-limit, контрактов и приоритезации | Shop API | Открытие API «завалило» MES — у партнёров одни и те же ресурсы, что у B2C. Нет защиты от лавины. |
| P10 | Партнёры не получают уведомлений о статусе заказа | Shop API | Их единственный способ узнать статус — спрашивать. Возникает шум в саппорт и потеря контрактов. |
| P11 | Расчёт цены — «чёрный ящик» без кеша | MES API | Повторный расчёт похожих/одинаковых моделей идёт с нуля. По хешу модели можно отдавать ответ за миллисекунды. |
| P12 | Нет SLA и приоритезации очередей | MES + RabbitMQ | B2C и B2B стоят в одной очереди, дорогой клиент ждёт за дешёвым. |

### 2.2 Потенциальные риски

- **Линейный рост заказов** — текущая архитектура не выдержит ещё пары кварталов даже без открытия новых рынков.
- **Безопасность API** — в задании нет упоминания rate-limit, токенов и аудита для B2B; вероятная уязвимость.
- **DR/бэкапы** — состояние неизвестно. Single-instance БД без описанной стратегии бэкапа — серьёзный риск.
- **Стоимость S3** — 3D-файлы продолжат накапливаться. Нужна политика жизненного цикла (move to cold storage).
- **Команда** — 8 инженеров на 3 системы. Тимлид — бывший C#-разработчик, специализированной экспертизы по архитектуре/SRE в команде нет.

## 3. Инициативы

Сгруппированы по тематике. У каждой инициативы — короткое описание и какую проблему она закрывает.

### Группа A. Наблюдаемость
- **A1. Метрики (Prometheus + Grafana).** RED для HTTP-эндпоинтов, USE для инфры. Закрывает P1.
- **A2. Распределённый трейсинг (OpenTelemetry SDK + Jaeger).** Покрытие всех 4 бэкендов и шины RabbitMQ. Закрывает P1, помогает P6.
- **A3. Централизованное логирование (Loki/OpenSearch + Promtail/Fluent Bit).** Закрывает P1, помогает поддержке.

### Группа B. Производительность MES
- **B1. Кеш дашборда MES (Redis).** Список «активные заказы по статусам» — горячие данные. Закрывает P4.
- **B2. Асинхронный расчёт цены.** Выделить worker, который слушает очередь, кладёт результат в БД и публикует событие. Закрывает P2.
- **B3. Кеш расчётов по хешу 3D-модели.** Идентичная или близкая (по полигональности/материалу) модель — отдаём ранее посчитанную цену. Закрывает P11.

### Группа C. Надёжность и масштабирование
- **C1. Перенос приложений в Kubernetes.** HPA, rolling deploy, изоляция ресурсов. Закрывает P5.
- **C2. Read replicas для PostgreSQL.** Разгружает основной инстанс для тяжёлых SELECT (дашборд, отчёты). Закрывает P5.
- **C3. Идемпотентность и DLX в RabbitMQ.** Уникальный ключ сообщения + ретраи + хранение «дохлых» сообщений в DLX-очереди. Закрывает P6.

### Группа D. B2B-канал
- **D1. API-Gateway с rate-limit, токенами и аудитом.** Закрывает P9.
- **D2. Webhook-уведомления партнёрам о смене статуса.** Закрывает P10.
- **D3. Раздельные очереди и приоритеты для B2C/B2B.** Закрывает P12, P3.

### Группа E. Процессы и команда
- **E1. Автоматизация E2E.** QA уже хочет и делал прототипы — поддержать. Закрывает P7.
- **E2. CI/CD до prod автоматически после прохождения тестов.** Закрывает P8.
- **E3. Найм:**
  - **SRE/Platform** — выстроить мониторинг, K8s, CI/CD. Сейчас 1 DevOps на всё.
  - **Backend Java/C#** — под распил MES и реализацию воркера расчёта.
  - **Без найма всё перечисленное растягивается на год+.**

## 4. Приоритизация

Использую модель «Impact / Effort» — что даёт максимум эффекта при минимальных трудозатратах,
и учитываю **зависимости**: не оптимизируем то, чего не измеряем.

| Инициатива | Impact | Effort | Срочность | Приоритет |
|---|---|---|---|---|
| A1 Метрики | Высокий | Низкий | Сейчас | **P0** |
| A2 Трейсинг | Высокий | Средний | Сейчас | **P0** |
| C3 Идемпотентность + DLX | Высокий | Низкий | Сейчас | **P0** |
| B1 Кеш дашборда MES | Высокий | Низкий | Сейчас | **P1** |
| B2 Асинхронный расчёт цены | Высокий | Средний | Сейчас | **P1** |
| A3 Логирование | Средний | Средний | Скоро | **P1** |
| D1 API-Gateway + rate-limit | Высокий | Средний | Скоро | **P1** |
| C1 Kubernetes | Высокий | Высокий | Скоро | **P2** |
| E1 Автоматизация E2E | Средний | Средний | Скоро | **P2** |
| D2 Webhook'и | Средний | Низкий | Позже | **P2** |
| B3 Кеш расчётов по хешу | Средний | Средний | Позже | **P2** |
| D3 Приоритезация очередей | Средний | Низкий | Позже | **P2** |
| C2 Read replicas | Средний | Низкий | Позже | **P3** |
| E2 Авто-деплой prod | Низкий | Низкий | Позже | **P3** |
| E3 Найм | Высокий | — | Сразу | **P0 параллельно** |

### Логика приоритизации

- **A1/A2 идут первыми**, потому что без них любое оптимизационное действие — гадание. Бизнесу это объяснить тяжелее всего, но это фундамент.
- **C3 (идемпотентность + DLX)** идёт в P0 при низком Effort — это прямой ответ на «пропавшие заказы», крупнейшую боль клиентов сегодня. Закрывается одним спринтом.
- **B1/B2** — самая громкая боль операторов и пользователей API. После того как метрики покажут, где именно тормозит.
- **C1 Kubernetes** — большой эпик. Делается параллельно остальному, но не заменяет точечные оптимизации.
- **E3 Найм** не имеет дедлайна, но запускается **сразу**: между «договорились» и «человек на работе» — 2–3 месяца.

## 5. Целевая архитектура через полгода

Что должно быть видно на C4-диаграмме через 6 месяцев:

1. **Все 4 бэкенда (Shop API, CRM API, MES API, новый Price-Calculator-Worker) контейнеризированы и работают в Kubernetes.** Каждый — за HPA, по 2+ реплики.
2. **MES распилен на части:**
   - тонкий MES API (синхронные CRUD + read из кеша)
   - Price-Calculator-Worker (асинхронный, слушает RabbitMQ, кладёт результат и эмитит событие)
3. **Redis-кеш** для дашборда MES (списки заказов по статусам) и для результатов расчёта цены (ключ = хеш 3D-модели).
4. **Все сервисы экспортируют метрики (Prometheus) и трейсы (OTLP → Jaeger).** Trace context пробрасывается через HTTP-заголовки **и** через свойства RabbitMQ-сообщений.
5. **Логи в Loki**, дашборды и алёрты в Grafana.
6. **API-Gateway перед Shop API** для B2B: rate-limit, JWT-аутентификация, аудит, webhook'и для уведомлений партнёров.
7. **PostgreSQL: primary + read replica** для каждой БД (Shop DB, MES DB, CRM DB).
8. **RabbitMQ: DLX, идемпотентные обработчики, раздельные очереди для B2C и B2B.**
9. **CI/CD: автоматический E2E + автоматический деплой до prod при «зелёных» тестах**, ручной gate только для major-релизов.

В команде: новый SRE, +1 бекенд (Java или C#), QA-инженер вышел на автоматику.

## 6. Топ-3 инициативы, если можно только три

Если бы был лимит — **три эпика на ближайшие 6 месяцев**:

### № 1. Наблюдаемость: метрики + распределённый трейсинг (A1 + A2)
Объединил в один пункт — они дают эффект только вместе.

**Почему первым:** сейчас команда не может ответить на простой вопрос «где зависает заказ» —
ни клиенту, ни себе. До тех пор пока этого нет, любая оптимизация — лотерея, и любое объяснение
бизнесу — «не знаю». Стоит дёшево (готовые стеки Prometheus/Grafana/Jaeger/OTel),
эффект мгновенный — за пару спринтов появляется доказательная база для всех остальных решений.

**Что закрывает:** P1 полностью, частично P6 (видны зависшие/потерянные сообщения).

### № 2. Идемпотентность сообщений + DLX в RabbitMQ (C3)
**Почему вторым:** это **прямая причина** «пропавших» заказов, на которую жалуются и клиенты,
и партнёры. Стоит мало — изменения только в сериализации сообщений (добавить `message_id`)
и в конфигурации RabbitMQ (DLX). Делается одним спринтом. Эффект — каждая попавшая в систему
заявка либо доходит, либо лежит в DLX (видна и пригодна для ретрая) — но не теряется молча.

**Что закрывает:** P6 полностью. Останавливает отток клиентов.

### № 3. Асинхронный расчёт цены + кеш дашборда MES (B2 + B1)
**Почему третьим:** это **самая громкая боль операторов и B2B-партнёров**: операторы не могут
работать с дашбордом, заказы «зависают» на этапе расчёта из-за того, что один тяжёлый расчёт
блокирует поток.

Технически это две вещи в одной плоскости:
- Вынести расчёт в отдельный воркер, слушающий RabbitMQ — MES API мгновенно отвечает «принято»,
  результат прилетит событием.
- Закешировать дашборд (список заказов по статусам) в Redis с инвалидацией по событиям смены
  статуса.

**Что закрывает:** P2, P4. Снимает нагрузку с MES API, освобождает место в очереди для B2B.

### Что осознанно отложил

- **Kubernetes (C1)** — большой эпик на 2–3 квартала. Без него полгода прожить можно
  (текущая инфра EC2 + Managed PostgreSQL работает), а без наблюдаемости — нельзя.
- **API-Gateway (D1), webhook'и (D2)** — снимают боль партнёров, но не корневые причины.
  Имеют смысл после того, как заказы вообще перестанут теряться (после №2).
- **Read replicas (C2)** — оптимизация-вдогонку. Сначала смотрим в метрики (после №1), где
  именно болит, потом решаем, нужны ли они.
- **Авто-деплой prod (E2)** — экономит часы, но без E2E-автоматики (которая сама требует
  спринтов) рискованно. Не успеваем за полгода без жертв.

## 7. Резюме

Архитектура «Александрита» — типичный кейс монолитов, которые «росли как могли», и теперь
не справляются с открытием B2B-канала. Корневая причина 80% жалоб — **отсутствие наблюдаемости**
(не видим, где болит) и **синхронная обработка тяжёлых расчётов** в MES (одно тяжёлое изделие
блокирует поток).

**Что делать в ближайшие 6 месяцев:**
1. Включить наблюдаемость — метрики и трейсинг (фундамент).
2. Закрыть утечку сообщений в RabbitMQ (быстрый win по самой громкой жалобе клиентов).
3. Распилить расчёт цены на асинхронный воркер и закешировать дашборд MES (снимает боль операторов).
4. Параллельно — нанимать SRE и доп. бэкендера, чтобы оставшиеся эпики (K8s, B2B-Gateway,
   автоматизация QA) делались следующим полугодием.
