# Выбор и настройка мониторинга в системе

## 1. Мотивация

Сегодня единственный источник данных о работе системы — Яндекс.Метрика, которая измеряет
поведение пользователей в браузере (Shop UI). После открытия API для B2B-партнёров эта
картина перестала быть полной:

- значительная часть заказов приходит через API, минуя UI — Метрика их не видит;
- ни одна из бэкенд-метрик (RPS, латентность, ошибки, длина очередей RabbitMQ, использование
  ресурсов БД) сегодня не собирается;
- команда не может ответить на простые вопросы: «сколько заказов сейчас в статусе X»,
  «какая средняя длительность расчёта цены», «какой сервис тормозит», «не растёт ли DLQ»;
- инциденты разбираются со слов клиентов — это медленно и неполно.

### Что даст мониторинг бизнесу
1. **Снижение оттока клиентов.** Сейчас компания теряет крупные контракты из-за молчащих
   заказов. Мониторинг показывает, на каком статусе заказ зависает — и команда может
   реагировать **до** того, как клиент напишет жалобу.
2. **Обоснованное планирование роста.** Видя кривые RPS и латентности, можно заранее
   понять, когда нужно докупать ресурсы — а не догонять инциденты.
3. **Снижение MTTR.** Любая будущая ошибка диагностируется по метрикам/дашбордам, а не
   через VPN в продакшен.
4. **Платформа для SLO.** На метриках строятся SLI/SLO и обещания партнёрам по API.
5. **База для аварийного реагирования.** Алёрты освобождают команду от ручного мониторинга
   глазами в дашборды.

### На какие технические/бизнес-метрики мы повлияем
- **Доля «зависших» заказов** (бизнес) — снижение целевое в разы.
- **MTTR** (тех.) — с «несколько часов опроса клиента» до десятков минут.
- **Lead time для деплоя фикса** — быстрее ловим регрессию (заметим на графиках, а не через жалобу).
- **Conversion rate в воронке заказа** — впервые увидим, на каком шаге уходят пользователи в Shop UI.
- **Стоимость инфраструктуры** — мониторинг покажет, где переплачиваем за неиспользуемые мощности.

## 2. Выбор подхода к мониторингу

Используем **разные подходы для разных слоёв системы**. Это явная рекомендация задания
и хороший паттерн в реальной практике.

| Часть системы | Подход | Почему |
|---|---|---|
| HTTP API (Shop API, CRM API, MES API) | **RED** (Rate, Errors, Duration) | Это запрос-ориентированные сервисы; именно RED отвечает на «как нам сейчас работается с точки зрения клиента». |
| Инфраструктура (PostgreSQL, RabbitMQ, EC2/K8s ноды) | **USE** (Utilization, Saturation, Errors) | Это ресурсы; USE отвечает на «есть ли у нас запас». |
| Критические user-journey (оформление заказа, расчёт цены, дашборд MES) | **Четыре золотых сигнала** (Latency, Traffic, Errors, Saturation) | Это пользовательские сценарии end-to-end; Golden Signals — расширение RED, удобное для сложных композитных потоков и SLO. |
| Бизнес-процесс заказа | Кастомные **бизнес-метрики** | RED/USE не отвечают на «сколько заказов в статусе X». Это отдельный слой. |

## 3. Метрики и ярлыки

### 3.1 HTTP API — RED (применяется к Shop API, CRM API, MES API)

| Метрика | Тип | Ярлыки | Зачем |
|---|---|---|---|
| `http_requests_total` | counter | `service`, `method`, `route`, `status_code`, `channel` | Rate. `channel` (b2c/b2b) — ключевой, чтобы отделить нагрузку партнёров от пользователей онлайн-магазина. |
| `http_request_duration_seconds` | histogram | `service`, `method`, `route` | Duration. Histogram, чтобы строить p50/p95/p99 и SLO. |
| `http_requests_in_flight` | gauge | `service` | Concurrency — помогает поймать «затыки» воркеров. |
| `http_errors_total` | counter | `service`, `route`, `error_type` (4xx/5xx/timeout) | Errors. `error_type` отделяет ошибки клиента от наших. |

**Реализация**:
- Spring Boot → micrometer + `micrometer-registry-prometheus`.
- C# (MES API) → `prometheus-net.AspNetCore`.

### 3.2 Бизнес-метрики (Golden Signals для пайплайна заказа)

| Метрика | Тип | Ярлыки | Зачем |
|---|---|---|---|
| `orders_created_total` | counter | `channel` (b2c/b2b), `source` (shop/api), `country` (под рост на новые рынки) | Traffic бизнес-уровня. |
| `orders_in_status` | gauge | `status` (INITIATED, FILE_UPLOADED, SUBMITTED, PRICE_CALCULATED, ...) | Снимок воронки. Видно, где «пробка». |
| `order_status_transition_duration_seconds` | histogram | `from_status`, `to_status`, `channel` | Найти «медленные» переходы — например, SUBMITTED → PRICE_CALCULATED. |
| `price_calculation_duration_seconds` | histogram | `complexity_bucket` (low/medium/high) | Подтвердить гипотезу про 2-30 минут расчёта и SLO для воркера. |
| `price_calculation_in_flight` | gauge | — | Сколько расчётов сейчас параллельно — насыщенность воркера. |
| `orders_lost_total` | counter | `stage`, `reason` | Зафиксировать «потерянные» заказы (попали в DLQ, timeout, ошибка). |

### 3.3 RabbitMQ — USE (через `rabbitmq_exporter`)

| Метрика | Тип | Ярлыки | Зачем |
|---|---|---|---|
| `rabbitmq_queue_messages_ready` | gauge | `queue`, `vhost` | Длина очереди — Saturation. |
| `rabbitmq_queue_messages_unacknowledged` | gauge | `queue` | «Висящие» сообщения у потребителей. Подозрение на медленный консьюмер. |
| `rabbitmq_queue_consumers` | gauge | `queue` | Достаточно ли потребителей. |
| `rabbitmq_queue_message_published_total` | counter | `queue` | Утилизация. |
| `rabbitmq_dlx_messages_total` | counter | `queue` | **Критическая метрика** — заказы, попавшие в DLX. Прямой индикатор «потерянных» заказов. |

### 3.4 PostgreSQL — USE (через `postgres_exporter`)

| Метрика | Тип | Ярлыки | Зачем |
|---|---|---|---|
| `pg_stat_activity_count` | gauge | `datname`, `state` | Сколько коннектов, в каком состоянии. Saturation для пула. |
| `pg_locks_count` | gauge | `datname`, `mode` | Точки блокировок, особенно при тяжёлых запросах дашборда MES. |
| `pg_stat_database_xact_commit_total` / `rollback_total` | counter | `datname` | Healthy throughput + доля откатов = индикатор ошибок. |
| `pg_database_size_bytes` | gauge | `datname` | Рост базы — планирование ресурсов. |
| `pg_stat_replication_lag_seconds` | gauge | `replica` | Когда появятся read replicas. |
| `pg_stat_user_tables_seq_scan_total` | counter | `datname`, `table` | Полные сканы — индикатор пропущенных индексов (история жалобы MES). |

### 3.5 Хост / Runtime

**Node (EC2 → K8s)** через `node_exporter`:
- CPU utilization, memory, disk I/O, fs usage, network — стандартный USE-набор.
- Ярлыки: `instance`, `region`, `role` (web/api/db/queue).

**JVM** (Shop API, CRM API):
- `jvm_memory_used_bytes{area=heap}`, `jvm_gc_pause_seconds`, `jvm_threads_states`.

**.NET** (MES API):
- `dotnet_collection_count_total`, `dotnet_threadpool_queue_length`, `process_working_set_bytes`.

### 3.6 Frontend (RUM)

- В Shop UI уже стоит Яндекс.Метрика — оставляем её для маркетинга и поведения пользователей.
- Дополнительно — **web-vitals** (LCP, FID/INP, CLS) с отправкой в свой Prometheus
  (через push-gateway или OpenTelemetry browser SDK), особенно для CRM и MES UI, которыми
  пользуются продавцы и операторы и которые сегодня не охвачены Метрикой.

### 3.7 Что я добавил **сверх** типичного списка

- `orders_lost_total` — специально под боль «потерянных заказов».
- `channel` как сквозной ярлык на бизнес-метриках — критично, чтобы видеть B2C vs B2B
  отдельно. Это прямо вытекает из ситуации с открытием API.
- `complexity_bucket` для `price_calculation_duration_seconds` — без него гистограмма будет
  «размазана» (разница 2 минуты vs 30 минут).

### 3.8 Что **не** взяли (и почему)

- Бесконтрольное добавление высококардинальных ярлыков (например, `user_id`, `order_id`)
  — раздуло бы Prometheus за пару дней. Такие данные — в трейсинг (Task 3) и логи (Task 4),
  не в метрики.
- Метрики уровня SQL-запросов через приложение — это работа APM (например, Datadog) или
  трейсинга, не основного мониторинга.

## 4. План действий (драфт ТЗ)

Описано **высокоуровнево** — каждый пункт раскладывается в отдельную задачу на спринт.

### Инфраструктура мониторинга
1. Развернуть **time-series базу — Prometheus** в выделенном неймспейсе `monitoring`
   (когда будет K8s) или как managed-сервис Yandex Monitoring до этого. Retention 30 дней
   локально + долгосрочное хранилище (Thanos/VictoriaMetrics) на 1 год для трендов.
2. Развернуть **Grafana** для визуализации. Дашборды как код (provisioning + Git).
3. Развернуть **Alertmanager** с группировкой и роутингом в Slack/Telegram/PagerDuty.

### Exporters
4. **node_exporter** — на каждой EC2-машине (или DaemonSet в K8s).
5. **postgres_exporter** — рядом с каждой PostgreSQL-БД (Shop DB, MES DB и CRM DB
   когда она будет видна на схеме).
6. **rabbitmq_exporter** — рядом с RabbitMQ.

### Инструментирование сервисов
7. **Shop API** (Spring Boot) — подключить `micrometer-registry-prometheus`, открыть
   `/actuator/prometheus`.
8. **CRM API** (Spring Boot) — то же.
9. **MES API** (C#) — `prometheus-net.AspNetCore`, `/metrics`.
10. Добавить **бизнес-метрики** (см. 3.2) в коде сервисов, ответственных за смену
    статуса заказа. Использовать константы статусов из общего модуля.

### Frontend
11. В **CRM UI** и **MES UI** — отправлять web-vitals в OpenTelemetry browser SDK →
    OTel Collector → Prometheus. Shop UI оставить с Метрикой.

### Дашборды
12. Создать набор дашбордов:
    - **API Health** (RED) на сервис.
    - **Order Pipeline** — снимок воронки по статусам, кривая прироста, время в каждом статусе.
    - **RabbitMQ Health** — длина очередей, DLQ, потребители.
    - **PostgreSQL Health** — коннекты, блокировки, размер, репликация.
    - **Infra (USE)** — CPU/RAM/Disk/Net по нодам.
    - **JVM / .NET runtime**.

### Алёрты
13. На каждый дашборд — алёрт-правила, выровненные по SLO (см. раздел 5).

### Документация
14. Runbook-и: «что делать, если DLQ растёт», «что делать, если p95 латентности > X»,
    «что делать, если падает скорость расчётов».

### Найм/команда
15. Подключить **SRE/Platform-инженера** (см. инициативу E3 из Task 1) — мониторинг
    самостоятельно не живёт без оператора.

## 5. Показатели насыщенности и реакция системы

> Доп. задание из условий.

Для каждого порога определены два уровня: **warning** (ещё есть запас, но смотрим) и
**critical** (нужно действовать сейчас). Действия идут от «мягких» (тикет, уведомление)
к «жёстким» (звонок дежурному, автоматическое масштабирование).

| Ресурс / метрика | Warning | Critical | Действие на warning | Действие на critical |
|---|---|---|---|---|
| CPU узла | > 75% 5 мин | > 90% 5 мин | Тикет в Jira | PagerDuty звонок дежурному + автомасштабирование (когда будет HPA в K8s) |
| Heap (JVM) / Working set (.NET) | > 80% | > 90% | Уведомление в Slack | Page + рестарт пода (для K8s) и тикет на расследование утечки |
| `http_request_duration_seconds{p95}` API | > SLO × 1.5 на 5 мин | > SLO × 3 на 5 мин | Slack | Page |
| `http_errors_total` 5xx rate | > 1% | > 5% | Slack | Page |
| `rabbitmq_queue_messages_ready` (на основных очередях) | > 1000 5 мин | > 10000 5 мин | Slack | Page + автоматически попытка scale-up consumers |
| `rabbitmq_dlx_messages_total` | прирост > 0 за 5 мин | прирост > 10 за 1 мин | Slack | **Немедленный page** — это потерянные заказы |
| `pg_stat_activity_count{state=active}` к `max_connections` | > 70% | > 90% | Slack | Page + анализ зависших транзакций |
| `pg_stat_replication_lag_seconds` | > 30 сек | > 5 мин | Slack | Page |
| `price_calculation_in_flight` | > N₁ (TBD по нагрузке) | > N₂ | Slack | Page + автоматическое наращивание воркеров |
| Disk usage | > 75% | > 90% | Тикет | Автоматический cleanup + page |

### Принципы выбора порогов
1. **Warning ≈ 0.75 × Critical.** Даёт 1–2 часа реакции до того, как «загорится».
2. **Critical < 100%.** Никогда не алёртить на 95%+ utilization — к тому моменту уже поздно.
3. **Хитрые пороги для очередей:** не абсолютное значение, а **скорость роста**
   (`rate(rabbitmq_queue_messages_ready[5m])`). Очередь длиной 1000 — норма, если стабильно;
   беда — если она удваивается каждую минуту.
4. **DLQ — особый случай:** любой прирост — это потерянное сообщение, поэтому warning =
   «появился прирост», critical = «прирост быстрый».

### Канал доставки алёртов
- **Slack/Telegram** (warning) — без шума, в командный канал.
- **PagerDuty/Opsgenie + автодозвон** (critical) — дежурному инженеру (24/7 ротация).
- **Тикет в Jira** (для не-срочных, требующих расследования).
- Письма в саппорт компании — нет: уведомления о клиентских проблемах должны быть в
  Slack-канале саппорта, чтобы не теряться в почте.

## 6. Что в первую очередь

Если делать поэтапно — следующий порядок (даёт максимум пользы при минимальном вложении):

1. **Спринт 1.** Prometheus + Grafana + node_exporter + postgres_exporter + rabbitmq_exporter.
   На этом уровне уже видна вся инфра, и часть бизнес-сигналов (длина очередей, рост БД,
   utilization). Это работает **без изменений в коде сервисов**.
2. **Спринт 2.** Инструментирование Shop API (RED). Самый нагруженный B2C — увидим
   реальную картину пользовательского трафика.
3. **Спринт 3.** Инструментирование CRM API и MES API + бизнес-метрики `orders_*` и
   `price_calculation_*`. С этого момента появляется ответ на «где зависают заказы».
4. **Спринт 4.** Алёрты + первые runbook'и. Уход от «глаз в дашборды» к реактивной модели.
5. **Параллельно** — RUM в CRM/MES UI (когда web-vitals критичны для пользовательского опыта
   операторов).

## 7. Резюме

- Используем **разные подходы** для разных слоёв: **RED** для HTTP API, **USE** для
  инфраструктуры, **Golden Signals** для критичных пользовательских сценариев,
  **бизнес-метрики** для пайплайна заказа.
- Технологический стек — **Prometheus + Grafana + Alertmanager + набор exporter'ов**.
  Серебряная пуля курса; стек открытый, бесплатный, хорошо интегрируется с K8s, в команде
  нет специальных навыков для его освоения.
- Ярлыки — **сквозной `channel` (b2c/b2b)** обязателен для всех бизнес-метрик. Высокую
  кардинальность (`order_id`, `user_id`) держим в трейсинге/логах, не в метриках.
- **Стартуем с инфраструктуры** (exporter-ы, без изменений в коде), параллельно
  инструментируем сервисы.
- **Особо болезненная метрика** — прирост в DLQ — критический алёрт с первого дня, потому
  что каждое сообщение там = потерянный заказ.
