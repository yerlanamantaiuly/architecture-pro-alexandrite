# Архитектурное решение по логированию

## 1. Мотивация

Сегодня **разбор любой нестандартной ситуации начинается со слов клиента**:
«у меня заказ № X завис», «партнёр пишет, что не получил уведомление», «оператор
жалуется на ошибку». Дальше специалист поддержки/разработчик идёт **по очереди в
каждый сервис**, открывает локальные файлы логов (каждый — со своим форматом и
ротацией), пытается сопоставить временные метки и угадать, какие из сотен строк
относятся к нужному заказу.

Результат:
- разбор одного инцидента занимает часы;
- многие проблемы остаются нераскрытыми («не нашли причину»);
- знание о типичных ошибках не накапливается, потому что нет единого места для поиска;
- DDoS или аномальные всплески запросов невозможно заметить заранее — только постфактум.

### Что даст централизованное логирование
1. **Один поиск по всем 4 бэкендам + RabbitMQ + БД** — за минуты, а не часы.
2. **Корреляция с трейсами через `trace_id`** — из жалобы клиента находим конкретный
   запрос, видим всю цепочку логов по нему.
3. **Алертинг на паттерны** — «появилось 5+ строк `OutOfMemoryError` за минуту»,
   «доля ERROR превысила 5%», «10 000 заказов за секунду — возможный DDoS».
4. **Аудит** — кто изменил статус заказа, когда, с какого хоста.
5. **Доказательная база для общения с партнёрами** — «вот тайминги, ваш заказ
   обработан за 12 секунд, проблема не на нашей стороне».

### Технические и бизнес-метрики решения

| Метрика | Тип | Сейчас | Цель |
|---|---|---|---|
| **MTTR инцидента с заказом** | Тех. | часы | минуты |
| **Доля «нераскрытых» жалоб (не нашли причину)** | Тех./бизнес | высокая | <5% |
| **Время на сбор информации для общения с B2B-партнёром** | Бизнес | десятки минут | секунды |
| **Среднее число консультаций «как было до» (запросы инженеров к саппорту)** | Тех. | высокое | низкое (всё в логах) |
| **Процент инцидентов, найденных алёртом (а не клиентом)** | Тех./бизнес | 0% | >50% за полгода |

## 2. Какие логи собирать и откуда

### 2.1 Системы, из которых собираем логи

На диаграмме [`jewerly_c4_model_logging.drawio`](./jewerly_c4_model_logging.drawio) —
красным отмечены источники логов и компоненты стека. Источники:

| Источник | Что логируем | Приоритет |
|---|---|---|
| **Shop API** (Spring Boot) | Запросы B2C/B2B, создание/изменение заказа, загрузки 3D, ошибки | P0 |
| **CRM API** (Spring Boot) | Изменение статуса заказа, подтверждение производства, обмен с RabbitMQ | P0 |
| **MES API** (C#) | Расчёт цены, изменение статуса, обмен с RabbitMQ, ошибки воркеров | P0 |
| **RabbitMQ** | Системные логи: подключения, ошибки роутинга, DLX события | P1 |
| **PostgreSQL** | Slow queries (`log_min_duration_statement`), ошибки | P1 |
| **Frontend (Shop / CRM / MES UI)** | Клиентские JS-ошибки (Sentry или отдельный канал) | P2 |
| **Инфраструктура (K8s, nginx/ingress)** | Доступы, ошибки, deployment events | P2 |

### 2.2 Структура лога (JSON, обязательно)

Структурированный лог — это **JSON c фиксированным набором полей**, а не свободный
текст. Без структуры теряется половина пользы Loki/ELK/etc.

```json
{
  "timestamp": "2026-05-28T17:42:13.482Z",
  "level": "INFO",
  "service": "shop-api",
  "environment": "prod",
  "trace_id": "eb16de9f27d1702f9b06a4965d05ff99",
  "span_id": "1b7aa106c8e4f312",
  "event": "order.status_changed",
  "order_id": "ord_8421",
  "channel": "b2b",
  "status_from": "SUBMITTED",
  "status_to": "PRICE_CALCULATED",
  "actor": "system",
  "duration_ms": 247312,
  "message": "Order status updated"
}
```

Ключевые поля во всех логах системы:
- `timestamp` (ISO 8601, UTC)
- `level` (DEBUG/INFO/WARN/ERROR/FATAL)
- `service` (стандартное имя сервиса)
- `environment` (dev/release/prod)
- `trace_id` / `span_id` — **обязательная связь с трейсингом** (Task 3)
- `event` — короткое имя события (`order.created`, `order.status_changed`,
  `price.calculation.completed`, `auth.login.failed`, ...)
- `message` — человекочитаемое описание

И **кастомные поля под событие**.

### 2.3 Список INFO-логов (бизнес-события)

| # | Событие | Где | Поля сверх стандартных |
|---|---|---|---|
| L1 | `order.created` | Shop API | `order_id`, `customer_id` (хеш), `channel`, `items_count`, `total_price_estimate` |
| L2 | `order.file_uploaded` | Shop API | `order_id`, `file_size_bytes`, `polygon_count`, `file_format` |
| L3 | `order.status_changed` | Shop API / CRM API / MES API | `order_id`, `status_from`, `status_to`, `actor`, `duration_in_prev_status_ms` |
| L4 | `price.calculation.started` | MES API | `order_id`, `polygon_count`, `complexity_bucket` |
| L5 | `price.calculation.completed` | MES API | `order_id`, `duration_ms`, `final_price`, `cache_hit` (когда будет кеш) |
| L6 | `rabbitmq.message.published` | Shop/CRM/MES API | `queue`, `message_id`, `order_id` |
| L7 | `rabbitmq.message.consumed` | Shop/CRM/MES API | `queue`, `message_id`, `order_id`, `processing_duration_ms` |
| L8 | `b2b.api.request` | Shop API | `partner_id`, `endpoint`, `response_code`, `duration_ms` |
| L9 | `b2b.webhook.sent` | Shop API | `partner_id`, `order_id`, `event_type`, `response_code`, `retry_count` |
| L10 | `auth.login.success` | Shop/CRM/MES | `user_type` (customer/seller/operator), `user_id` (хеш), `ip` (опц., маскированный) |
| L11 | `operator.assigned` | MES API | `order_id`, `operator_id` (хеш) |
| L12 | `shipment.received` | CRM API | `order_id`, `carrier`, `tracking_number` (маскированный) |

> Идея пограничного отбора: INFO — это то, что **должен видеть бизнес в дашборде
> и саппорт при разборе инцидента**. Технические детали (SQL-запросы, retry,
> внутренние состояния) — это DEBUG.

### 2.4 Использование других уровней

| Уровень | Когда писать | Включён в prod | Алёрт? |
|---|---|---|---|
| **DEBUG** | Подробности обработки, значения переменных, тайминги внутренних шагов | Нет (по умолчанию). Включается **точечно** через env-flag для конкретного сервиса на N минут при расследовании | Нет |
| **INFO** | Бизнес-события из 2.3 | Да | Нет (отдельные события могут быть source для метрик) |
| **WARN** | Деградация, ретраи, fallback, отклонения от SLO без отказа (`circuit_breaker_open`, `retry_attempt`, `slow_query`, `cache_miss_storm`) | Да | Spike → Slack |
| **ERROR** | Ошибка операции (исключение), сервис продолжает работать (`order_save_failed`, `rabbitmq_publish_failed`, `unknown_message_format`) | Да | Spike → PagerDuty |
| **FATAL** | Критическая ошибка, сервис не может продолжить (нет коннекта к БД на старте, не загрузилась конфигурация) | Да | Любая → PagerDuty + page |

**Правила оформления:**
- DEBUG в prod — только временно, через runtime-флаг. Никогда не оставлять
  включённым «на всякий случай» (сжирает индекс, шумит).
- ERROR/FATAL **обязаны** содержать `error.type`, `error.message` и (для исключений)
  `error.stacktrace`.
- WARN/ERROR **обязаны** содержать `trace_id` — иначе бесполезны при разборе.

## 3. Что внедряем в первую очередь — приоритизация трейсинга и логирования

Команда не может реализовать одновременно полный трейсинг (Task 3) и полное
логирование (Task 4) на все 4 бэкенда + инфру. Поэтому план — поэтапный.

### Логика приоритезации

1. **Польза × дешевизна реализации**: автоинструментация vs ручная работа.
2. **Где больше всего «не видим»**: где сейчас слепые зоны (MES API — расчёт цены).
3. **Где больше всего пользователей жалоб**: «потерянные» заказы (RabbitMQ-связки).

### Очередь работ

| Спринт | Что | Почему |
|---|---|---|
| **Sprint 1–2** | **Структурированные логи (JSON) + сбор в Loki + Grafana** для **Shop API, CRM API, MES API** | Самая дешёвая инициатива — поменять формат логов и поднять стек. Сразу избавляемся от «бегать по EC2 и `grep` файлам». |
| **Sprint 2** | **Распределённый трейсинг (Task 3) для Shop API и CRM API** — auto-instrumentation Spring Boot одним javaagent. **Логи теперь имеют `trace_id`** | Spring-стек даёт максимум профита при минимуме кода. Соединяем логи и трейсы через `trace_id`. |
| **Sprint 3** | **Трейсинг MES API (C#)** + кастомные спаны на шаге расчёта цены | Здесь основная боль (длинный расчёт). Требует чуть больше кода, но критично. |
| **Sprint 3** | **Бизнес-логи в коде сервисов** (L1–L12 из раздела 2.3) | Добавляем нашему пайплайну заказов наглядность. |
| **Sprint 4** | **RabbitMQ + PostgreSQL** в Loki | Системные логи + slow query → теперь видим источник «потерянных» сообщений и тяжёлых SQL. |
| **Sprint 5** | **Алертинг и аномалии** (раздел 7) | После того как поток логов стабилизировался — навешиваем правила. |

**Идея:** логирование стартует **первым**, потому что:
- меньше кода, чем трейсинг (нужно только поменять формат + ship);
- работает на любом сервисе сразу, не зависит от инструментации;
- даёт немедленную пользу даже без `trace_id` (хотя без него хуже).

**Трейсинг догоняет в следующем спринте**, после чего связка «`trace_id` в логах»
становится главным инструментом инженера: из жалобы → нашли `trace_id` → подняли
все логи и весь трейс одним кликом.

## 4. Предлагаемое решение

### 4.1 Технологии

| Компонент | Технология | Почему |
|---|---|---|
| **Сбор логов с подов** | **Promtail** (DaemonSet) на каждой ноде K8s, или **OpenTelemetry Collector** в режиме agent | Уже сидит на ноде, читает `/var/log/pods`, добавляет K8s-лейблы (namespace, pod, service) автоматически. Стандарт индустрии. |
| **Хранение и поиск** | **Grafana Loki** | Индексирует логи **по labels**, не по содержимому — на порядок дешевле ES при сопоставимом UX. Идеален для нашего объёма (см. раздел 8 — сравнение). |
| **Object storage** | **S3 / Yandex Object Storage** | Loki кладёт chunks туда, дёшево, тёплый и холодный тиры. |
| **UI и алертинг** | **Grafana** | Та же Grafana, которая будет показывать метрики из Task 2 — единая точка наблюдения. Поддерживает LogQL, live tail, recording rules, alerting. |
| **Структурирование в коде** | Spring Boot → **logback + logstash-logback-encoder** (JSON-выход). C# (MES) → **Serilog** с JSON-sink. | Стандарт-де-факто в обеих экосистемах. |

### 4.2 Поток данных

```
[Shop API] [CRM API] [MES API] [RabbitMQ] [PostgreSQL]
    │         │         │         │           │
    │ stdout/stderr (JSON)
    └─────────┴─────────┴─────────┴───────────┘
                       │
                  [Promtail / OTel agent]
                       │  OTLP logs / Loki push API
                       ▼
                     [Loki]
                       │
                  chunks + index
                       ▼
              [S3 / Object Storage]

  Инженер ─→ [Grafana] ─→ LogQL ─→ [Loki] ─→ результат
```

### 4.3 Что меняется в коде сервисов

Минимально, **без переписывания**:
- Поменять appender'ы logback / Serilog на **JSON** (один файл конфигурации).
- Добавить в MDC / `LogContext` инжекцию `trace_id` и `span_id` из OpenTelemetry
  (готовые библиотеки `opentelemetry-logback-mdc` и `Serilog.Enrichers.OpenTelemetry`).
- В точках событий (L1–L12) — заменить `log.info("Created order " + id)` на
  `log.info("order.created", kv("order_id", id), kv("channel", channel), ...)`.

## 5. Политика безопасности

### 5.1 Что НЕ логируем

| Категория | Примеры | Что делать вместо |
|---|---|---|
| **ПДн** | ФИО, email, телефон, адрес, паспорт | Хеш SHA-256 от ID пользователя/email; ничего из этого не логировать в plain |
| **Платёжные данные** | Номер карты, CVV, BIN | НЕ собирать вообще. PCI-DSS scope не нужен. |
| **Секреты** | Токены, API-ключи, пароли, JWT (целиком) | Только наличие/тип; маскирование первых/последних 4 символов |
| **Тело запроса/ответа** | JSON-payload с пользовательскими данными | Только размер (`payload_size_bytes`) и контрольные поля (`event`, `order_id`) |
| **Файлы 3D-моделей** | Содержимое .stl/.obj | Только метаданные: `file_size_bytes`, `polygon_count`, `format` |

### 5.2 Реализация sanitization
- **На уровне приложения** — фильтр в logback/Serilog, который маскирует поля по
  имени (`email`, `phone`, `password`, ...).
- **На уровне Promtail/OTel-collector** — pipeline-стадии с regex-маскированием
  по паттернам (карты, номера паспортов).
- **Аудит** — раз в месяц перебор случайной выборки логов (script + ручная проверка)
  на наличие PII. Найденное — фикс на стороне приложения, выпиливание старых индексов.

### 5.3 Доступ к логам

| Роль | Доступ |
|---|---|
| **Engineer / Backend** | Read-only к логам своего сервиса (фильтр по namespace) |
| **SRE / Platform** | Read-write ко всему стеку, конфигурации Loki/Grafana |
| **Support** | Read-only ко всем сервисам, без админских настроек |
| **Audit/Compliance** (если появится) | Read-only к долгосрочному архиву |
| **Внешние** (B2B-партнёры, клиенты) | **НЕТ.** Если им нужны данные о статусе заказа — через отдельный B2B-портал или email-уведомления. |

Аутентификация — через корпоративный SSO (OIDC) с группами LDAP/GitHub Teams.
Grafana RBAC настроен на эти группы. Audit log самого Grafana — отдельный поток
в Loki (с retention > общего).

### 5.4 Транспорт
- В prod: TLS между сервисами → Promtail → Loki.
- Доступ к S3 — IAM-роль с минимальными правами (только nameseapace Loki).

## 6. Политика хранения

### 6.1 Отдельные индексы / streams

Loki не использует «индексы» как ES — он работает со **stream'ами по labels**.
Логическая нарезка:
- `service` (`shop-api`, `crm-api`, `mes-api`, `rabbitmq`, `postgres`, ...).
- `environment` (`prod`, `release`, `dev`).
- `level` — для быстрой фильтрации.

**Что отдельно:**
- **Audit logs** (кто что менял) — отдельный stream с большим retention (см. ниже).
- **Application logs** (бизнес + WARN/ERROR) — основной поток.
- **Access logs** (HTTP nginx/ingress) — отдельный stream, high-volume.

### 6.2 Retention (срок жизни)

| Тип логов | Hot (быстрый доступ) | Warm/Cold (S3) | Архив |
|---|---|---|---|
| Application logs (INFO/WARN/ERROR) | 14 дней | 90 дней | — |
| DEBUG (если включали) | 24 часа | — | — |
| Access logs | 14 дней | 30 дней | — |
| Audit logs | 90 дней | 1 год | бессрочно (на отдельном S3-bucket с lock) |
| Логи безопасности (auth, login fail) | 30 дней | 1 год | — |

**Обоснование:**
- Hot — для оперативного разбора инцидентов (за неделю-две, не дольше).
- Warm — для исторического анализа (тренды, разбор повторных инцидентов).
- Audit — для compliance и юридических запросов.

### 6.3 Объём (оценка)

Приблизительный расчёт:
- ~500 заказов в день, средняя цепочка ~30 лог-записей на заказ → 15 000 INFO-записей.
- Плюс WARN/ERROR (~5%) + системные/HTTP-access логи. Итого ~100 000 строк в день.
- Средний размер строки JSON ~500 байт → **~50 МБ в день**.
- 14 дней hot ≈ 700 МБ; 90 дней warm ≈ 4.5 ГБ.
- Сжатие в Loki ~10× → реально **70 МБ hot, ~450 МБ S3 warm**.

Это **очень небольшой** объём — выбор технологии не упирается в storage.

### 6.4 Что делать при росте
- При выходе на >10× нагрузки (5000 заказов/день) — пересматривать retention,
  добавлять sampling для DEBUG/INFO с низкой ценностью.
- При появлении долгосрочных требований (compliance) — отдельный архивный bucket
  с immutable lock.

## 7. От «сбора» к «анализу» — алертинг и аномалии

Просто хранилище логов — это «архив». Чтобы стало инструментом, нужны **активные
правила**.

### 7.1 Алертинг (Grafana Alerting на LogQL)

| Правило | Условие | Severity | Канал |
|---|---|---|---|
| **Error rate spike** | `rate({level="ERROR"}[5m]) > 5x avg_over_time` | warning | Slack |
| **FATAL appeared** | `count_over_time({level="FATAL"}[1m]) > 0` | critical | PagerDuty + page |
| **OOM / panic / fatal stacktrace** | `{message=~"OutOfMemoryError|panic:|fatal error"}` обнаружено | critical | PagerDuty + page |
| **Lost RabbitMQ message** | `{event="rabbitmq.message.consumed"}` отсутствует за 30 мин для `message_id`, для которого был `rabbitmq.message.published` | critical | PagerDuty |
| **Auth failure burst** | `rate({event="auth.login.failed"}[5m]) > 10/s` для одного `user_id` | warning | Slack + security |
| **B2B SLA violation** | `{event="b2b.api.request", duration_ms>60000}` — был ответ дольше 60 сек | critical | PagerDuty + аккаунт-менеджер партнёра |
| **Service silent** | `absent_over_time({service="X"}[10m])` — сервис не пишет ничего | warning | Slack — возможно, упал stdout |

### 7.2 Поиск аномалий

#### Что такое аномалия в нашем контексте
- **Внезапное изменение скорости события**: «обычно 50 заказов в час, сейчас 10 000»
  → DDoS или кривой клиент API.
- **Появление новых строк ошибок** — паттернов, которых не было неделю назад →
  регрессия после деплоя.
- **Гэп в логах** — нет записей по `order.status_changed` для статуса X два часа
  → пайплайн встал.
- **Изменение распределения**: 99% заказов B2C, а сейчас 80% — внезапный B2B
  спайк → проблема у партнёра.

#### Как ловить

| Тип | Подход |
|---|---|
| **Простые спайки** | LogQL `rate()` + recording rule + Grafana alert |
| **Новые паттерны ошибок** | Открытое решение `loghound` / `elastalert` (если перейдём на OpenSearch). Для Loki — periodic export + Python-скрипт с n-gram сравнением (custom) |
| **Гэпы** | LogQL `absent_over_time()` + alert |
| **Аномальное распределение** | Запись `rate by (channel)` + Grafana alert на резкое изменение пропорций |

#### Конкретный пример из задания
> «было четыре записи о создании заказов и за секунду их стало 10 000»

Реализация:
```promql
rate({event="order.created"}[1m])
```
В Grafana правило: если значение > 100× среднего за последние 24 ч → **critical**.
Альёрт уходит и в Slack, и в security-канал; на стороне Shop API при дальнейших
запросах включается rate-limit per `partner_id` (см. Task 1, инициатива D1
«API-Gateway с rate-limit»).

## 8. [Доп. задание] Сравнение технологий

Критерии выбора (минимум 5 по заданию — у меня 8):

| # | Критерий | Что измеряем | Вес |
|---|---|---|---|
| 1 | **Лицензия** | Можно ли свободно использовать в коммерческом продукте | Высокий |
| 2 | **TCO** | Cтоимость владения: лицензия + инфра + команда поддержки | Высокий |
| 3 | **Memory/CPU footprint** | Сколько ресурсов жрёт сам стек | Высокий (для нашей инфры — критично) |
| 4 | **Производительность поиска** | UX поиска на нашем объёме | Средний |
| 5 | **Интеграция с k8s + OTel** | Насколько «из коробки» подключается | Высокий |
| 6 | **Кривая обучения** | Сколько времени команде на освоение | Средний |
| 7 | **Возможности анализа** (alerting, ML, аномалии) | Что доступно «без доплат» | Средний |
| 8 | **Долгосрочное хранение** | S3-tiering, политики ретеншена | Средний |

### Сравнительная таблица

| Критерий | **ELK** (Elasticsearch + Logstash + Kibana) | **OpenSearch** | **Grafana Loki** (Recommended) | **Splunk** |
|---|---|---|---|---|
| **Лицензия** | Elastic License 2.0 (после 2021 — не open-source) | Apache 2.0 (полностью открытый форк ES от AWS) | AGPLv3 (open-source, free) | Проприетарная, платная |
| **TCO** | Бесплатно по лицензии, но прожорлив (4–8 ГБ RAM на ES-ноду) | Дешевле ELK (легче лицензионно), та же прожорливость | **Самый дешёвый**: индекс маленький, chunks в S3, малый RAM/CPU | **Очень дорого** ($/GB indexed) — для нас неподъёмно |
| **Memory footprint** | 4–8 ГБ на инстанс | 4–8 ГБ на инстанс | **0.5–1 ГБ** | Зависит от тарифа |
| **Поиск** | **Лучший** в классе (full-text, агрегации, ML) | Аналогично ELK | По labels быстрый; по содержимому — `grep`-стиль (нет инвертированного индекса). Менее мощный, но достаточный для разбора инцидентов | Лучший в классе |
| **Интеграция OTel/k8s** | Хорошая (Fluentd/Filebeat) | Хорошая | **Отличная (родная)**, та же Grafana, что для метрик | Через коннекторы |
| **Кривая обучения** | Средняя (DSL ES, Logstash pipeline) | Средняя | **Низкая** (LogQL ≈ PromQL — команда уже знает) | Низкая (UI), но проприетарный SPL |
| **Алерты / аномалии** | Платно (X-Pack) | Бесплатно, скромнее ML | Базовый алертинг бесплатно (Grafana Alerting), кастом-аномалии — внешними скриптами | Лучшие в классе, но платно |
| **Cold storage в S3** | ILM (через snapshot/restore) | Так же | **Родное** — Loki сам хранит chunks в S3 | Платно |

### Вердикт

**На нашем размере и стадии — Grafana Loki**.

Почему:
- **Объём логов мал** (~50 МБ/день, см. раздел 6.3) — мощь full-text-индекса ES
  здесь избыточна. LogQL `|=` и regex по содержимому хватает за глаза.
- **Команда не знает ELK**, но знает Prometheus/Grafana (предполагается из Task 2).
  LogQL — это «продолжение PromQL». Кривая обучения — дни.
- **TCO минимальный**: один Loki-инстанс на 0.5–1 ГБ + S3 для chunks. Никаких
  отдельных нод под Elasticsearch.
- **Единый UI с метриками** — инженер открывает Grafana и видит метрики (Task 2)
  и логи рядом, по тому же `trace_id`.
- **Лицензия AGPLv3** — open-source, ничего не платим, можно патчить.

### Когда стоит уйти с Loki

- Если вырастем до **миллионов записей в день** и понадобится сложный full-text-поиск
  с агрегациями — мигрируем на **OpenSearch** (не на ELK — лицензия).
- Если появятся **compliance-требования** уровня банков/госов — пересмотрим в сторону
  Splunk или OpenSearch + спец-фичи.
- Если **ML-аномалии** окажутся критичны и встроенные правила не справятся —
  тогда платный X-Pack / Splunk оправдан.

Это решение **сегодня**, не на 5 лет.

## 9. Резюме

- **Собираем JSON-логи со всех 4 бэкендов + RabbitMQ + PostgreSQL** через
  Promtail (DaemonSet) → Loki → Grafana → S3.
- **INFO-логи — бизнес-события** (создание/смена статуса заказа, расчёт цены,
  B2B-запросы) с обязательным `trace_id` (связка с Task 3).
- **Другие уровни**: DEBUG только точечно, WARN на деградацию, ERROR на исключения,
  FATAL на смерть сервиса.
- **Логирование в первую очередь**: оно дешевле и быстрее даёт ценность, чем
  трейсинг. Трейсинг догоняет в следующем спринте, и логи получают `trace_id`.
- **Безопасность**: запрет ПДн / секретов в логах; sanitization на уровне
  приложения + collector'а; доступ через SSO с RBAC.
- **Хранение**: 14 дней hot, 90 дней warm S3, отдельный долгосрочный архив для
  audit logs. Реальный объём — десятки МБ в день, ресурсами легко покрывается.
- **Алертинг**: spike error rate, FATAL, OOM, lost message, B2B SLA, silent service.
  Аномалии — спайки rate, гэпы, изменение распределений.
- **Выбор технологии**: **Loki** — оптимум по TCO/UX/совместимости/команде.
  ELK и Splunk избыточны для нашего объёма, OpenSearch — план B на случай 10×
  роста или ML-требований.
